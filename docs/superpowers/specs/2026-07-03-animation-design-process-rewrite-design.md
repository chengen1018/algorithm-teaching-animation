# Animation Design Process 改寫規格

## 目標

重整 `references/animation-design-process.md`，讓第一次閱讀這套工作流程的人能快速理解：誰負責什麼、何時需要詢問使用者、設計何時算完成，以及審查失敗或文件被修改後要回到哪一步。

本次只改善結構、措辭與資訊順序，不改變既有流程、角色權限、通過條件或回退規則。

## 讀者

- 執行 `DESIGN_DEVELOPMENT` 的動畫設計者
- 負責向使用者提問與轉交答案的協調者
- 依 `DESIGN_READY` 條件進行驗證的獨立審查者
- 想理解動畫設計流程的維護者

## 改寫原則

1. 先交代整體流程，再展開個別規則。
2. 一個段落只說明一個目的，避免在同一句中混合設計、審查、核准與回退。
3. 統一使用「設計者」「協調者」「獨立審查者」；保留 `DESIGN_DEVELOPMENT`、`DESIGN_READY`、Full Review、Delta Review 等正式流程名稱。
4. 將規則改寫成可執行的步驟、清單或決策表。
5. 合併重複說明，但不合併或刪除 canonical `DESIGN_READY` conditions，確保 reviewer 仍能逐項建立證據矩陣。
6. 明確區分阻塞性的核心問題與可採 best-effort 預設值的低影響細節。
7. 明確呈現固定順序：`DESIGN_READY`、獨立審查 `PASS`、使用者核准精確版本、進入 `CONTRACT`。

## 文件結構

### 1. 這份文件管什麼

簡短說明目的、必要輸入、正式產物及責任邊界。特別指出澄清問題只是完成設計的手段，不能取代 `animation_design.md`。

### 2. 整體流程

用六個依序執行的步驟呈現：

1. 讀取已確認的輸入與決策。
2. 找出會阻塞核心設計的資訊缺口。
3. 透過協調者分批向使用者澄清。
4. 完成動畫設計並記錄合理預設值與風險。
5. 逐項執行 `DESIGN_READY` 自檢。
6. 送交獨立審查，通過後取得精確版本核准。

### 3. 什麼需要詢問使用者

分成兩類：

- 核心問題：答案會改變演算法語意、主要心智模型、核心視覺語意、場景結構、教學弧線或高階節拍，因此會阻塞設計。
- 低影響細節：一般顏色、字體、間距、局部 timing、措辭或裝飾，不影響正確性、accessibility 或學習目標時，由設計者採合理預設值。

同一節保留核心問題的批次協定：設計者規劃小批問題；協調者一次只問一題並忠實記錄；整批完成後一次交還設計者更新與重新評估。

### 4. 動畫設計必須完成什麼

保留現有設計職責：目標與受眾、演算法語意、心智模型、誤解預防、範例選擇、視覺隱喻與視覺語意、結構與場景、資訊層級、教學弧線、高階節拍、推薦方案、替代方案、取捨，以及使用者決策與 best-effort 風險。

### 5. `DESIGN_READY` 通過清單

保留目前所有 canonical conditions，逐條改成簡潔、可檢查的句子。條件數量與語意不可因合併文字而改變。

### 6. 通過後的審查與核准

以固定順序說明：

```text
DESIGN_READY
  → 獨立審查 animation_design.md
  → animation_design_review.md = PASS
  → 使用者核准同一精確版本
  → 進入 CONTRACT
```

清楚說明審查 `PASS` 不能取代使用者核准，使用者核准也不能取代獨立審查。

### 7. 文件修改、重新審查與回退

使用決策表區分：

- 初次審查：Full Review。
- 核心語意、心智模型、視覺語意、教學弧線、場景結構、高階節拍或影響不明的修改：Full Review。
- 範圍明確、影響可完整追蹤的局部修改：Delta Review；若發現跨區影響，立即升級為 Full Review。
- 使用者直接修改：視為新版本，舊審查與核准失效。
- 審查未通過或下游發現核心缺口：停止下游工作並回到 `DESIGN_DEVELOPMENT`。

### 8. 禁止事項

將目前失敗條件整理成短清單，保留所有實質禁止行為，避免再重複前文的完整解釋。

## 驗證方式

改寫後進行以下檢查：

1. 對照舊版，確認每項 `DESIGN_READY` condition 都仍存在且語意相同。
2. 確認 Full Review 與 Delta Review 的適用條件沒有放寬。
3. 確認使用者編輯會使舊審查失效，且不得把沉默或單純編輯視為核准。
4. 確認審查與核准順序仍是 `DESIGN_READY → PASS → 精確版本核准 → CONTRACT`。
5. 確認核心缺口會回退到 `DESIGN_DEVELOPMENT`，且下游必須停止。
6. 搜尋是否仍有含糊的角色稱呼、過長段落、不必要重複或未定義占位文字。

## 不在本次範圍內

- 不修改其他角色契約或參考文件。
- 不新增、刪除或調整 `DESIGN_READY` 條件。
- 不改變 SHA-256、審查產物或外部核准規則。
- 不重新設計整體 ANIMATION_DESIGN 工作流程。

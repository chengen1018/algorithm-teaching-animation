# 動畫設計流程

## 1. 這份文件管什麼

這份文件定義 `DESIGN_DEVELOPMENT` 的執行方式與完成條件。

這個階段的核心工作，是決定動畫要如何教學與呈現演算法，並產出一份達到 `DESIGN_READY` 的 `animation_design.md`。提出澄清問題只是完成設計的手段，不能取代動畫設計本身。

### 必要輸入

開始設計前，設計者必須取得：

- 已確認的任務脈絡；
- 演算法名稱、變體與範例輸入；
- 目標受眾與學習目標；
- 動畫需求與相關專案契約；
- 所有已記錄的使用者決策。

### 正式產物

這個階段的正式產物是 `animation_design.md`。文件必須完整描述動畫的教學與呈現設計，並準備好接受獨立審查。

## 2. 整體流程

設計者與協調者必須依序完成以下步驟：

1. **讀取輸入**：確認任務脈絡、演算法語意、受眾、學習目標與既有使用者決策。
2. **找出核心缺口**：判斷是否仍有會實質改變核心設計的未決問題。
3. **分批澄清**：若有阻塞性核心問題，由設計者規劃小批問題，再由協調者逐題詢問使用者。
4. **完成動畫設計**：設計心智模型、視覺呈現、場景結構、教學弧線與高階動畫節拍，並記錄合理預設值及風險。
5. **執行 `DESIGN_READY` 自檢**：逐項確認本文件第五節的所有條件都有文件證據。
6. **送交審查與核准**：自檢全部通過後，停止新增設計內容，將該精確版本交給獨立審查者。只有審查通過後，才能請求使用者核准同一精確版本。

## 3. 哪些問題需要詢問使用者

### 需要詢問的核心問題

只有當答案會實質改變以下任一項時，問題才可以阻塞設計：

- 演算法語意；
- 主要心智模型；
- 核心視覺隱喻或視覺語意；
- 場景結構；
- 教學弧線；
- 高階動畫節拍。

### 核心問題的批次協定

當仍有阻塞性核心問題時，必須使用以下方式處理：

1. 設計者先規劃一小批彼此緊密相關、且完成下一步設計所必需的問題。不得把問題做成一長串問卷，也不得把無關決策混在同一批。
2. 每個問題都必須提供：
   - 一個具體建議；
   - 建議理由；
   - 接受該建議的重要取捨或後果；
   - 適合時提供簡潔選項。
3. 協調者每次只能向使用者提出一題。收到答案並忠實記錄後，才能問下一題。
4. 協調者不得重新詮釋、弱化、合併或悄悄替換使用者答案，也不得把設計者的建議當成使用者決定。
5. 如果答案仍有會實質改變設計的歧義，協調者應保留原意，並在同一批內提出一個聚焦的追問。
6. 整批問題全部回答完後，協調者才把完整答案一次交回設計者。不要每收到一個答案就要求設計者更新。
7. 設計者收到整批答案後，只更新一次設計，並重新評估所有核心缺口。如果仍有阻塞性問題，再規劃下一小批；已不影響設計的問題不再詢問。

### 不應阻塞的低影響細節

如果某個選擇不會改變演算法語意、主要心智模型、核心視覺語意、教學弧線或高階節拍，就不應阻塞設計。例如：

- 小幅顏色或字體調整；
- 間距與局部位置；
- 局部 timing；
- 一般措辭；
- 裝飾性選擇。

除非這些細節會影響 accessibility、正確性或學習目標，否則設計者應採用合理的 best-effort 預設值，在必要時記錄風險，然後繼續設計。使用者仍可在後續編輯循環中調整這些細節。

## 4. 動畫設計必須完成什麼

`DESIGN_DEVELOPMENT` 必須真正完成動畫設計，而不只是蒐集偏好或重述輸入。設計者必須完成：

- **目標與受眾**：說明觀眾是誰，以及動畫要幫助他們學會什麼。
- **演算法語意**：確認演算法變體、操作規則與關鍵狀態的意思。
- **主要心智模型**：定義觀眾應建立的理解方式，以及這個模型的適用界線。
- **誤解預防**：找出觀眾可能產生的誤解，並設計對應的預防方式。
- **範例輸入**：選擇適合教學的範例，並說明選擇理由。
- **視覺呈現**：定義核心視覺隱喻、穩定視覺語意及資料結構的呈現方式。
- **場景與資訊組織**：定義場景結構、畫面分區與資訊層級。
- **教學弧線**：安排從動機與鋪陳，到狀態變化、關鍵洞見與結論的推進方式。
- **高階動畫節拍**：讓重要狀態變化及因果關係可以被觀眾看見。
- **方案與取捨**：提出推薦設計，說明理由，並記錄重要替代方案及其取捨。
- **決策與風險**：忠實納入已確認的使用者決策，並清楚標示 best-effort 假設與風險。

每個設計選擇都必須服務已確認的受眾與學習目標。除非低階實作細節會改變觀眾看到或學到的內容，否則不要把 Manim 操作、逐格 timing 或其他實作細節寫成核心設計要求。

## 5. `DESIGN_READY` 通過清單

只有以下十五項條件全部通過，設計者才能把 `animation_design.md` 標記為 `DESIGN_READY`：

1. 設計目標與目標受眾已明確。
2. 演算法變體與操作語意沒有歧義。
3. 主要心智模型明確，且在技術上忠實呈現演算法。
4. 已辨識觀眾可能產生的誤解，並提供對應的預防方式。
5. 範例輸入適合教學，且文件已說明選擇理由。
6. 所有經 Reference Routing 判定適用的型別專用設計決策與教學風險都已處理。若沒有相符的型別參考，文件已記錄 best-effort 分類、具體覆蓋風險與強化獨立審查要求。
7. 核心視覺隱喻與穩定視覺語意已定義。
8. 資料或結構的呈現方式、場景結構與資訊層級已定義。
9. 教學弧線前後一致。
10. 高階動畫節拍能清楚呈現重要狀態轉換與因果關係。
11. 推薦設計與重要替代方案都有理由及取捨說明。
12. 所有重要使用者決策都已忠實納入。
13. 不再有未解決的阻塞性核心問題。
14. 只剩低影響未決項目，且每一項都已記錄風險與所採用的 best-effort 預設值。
15. `animation_design.md` 符合所有必要契約與自檢要求。

每項條件都必須能在 `animation_design.md` 中找到具體證據。只要有任何一項失敗或仍缺少證據，就不得宣告 `DESIGN_READY`。

## 6. 通過後：獨立審查與使用者核准

通過 `DESIGN_READY` 後，必須依照以下順序進行：

```text
DESIGN_READY
  → 獨立審查 animation_design.md
  → animation_design_review.md = PASS
  → 使用者核准同一精確版本
  → 進入 CONTRACT
```

具體規則如下：

1. 一旦十五項 `DESIGN_READY` 條件全部通過，設計者就必須停止提出設計問題，也不得再新增或擴充設計內容。
2. 協調者將這個精確版本的 `animation_design.md` 交給獨立審查者。
3. 獨立審查者必須建立 `animation_design_review.md`，並逐項檢查本文件第五節的每一個 canonical `DESIGN_READY` condition。
4. 如果審查結果不是 `PASS`，設計必須回到 `DESIGN_DEVELOPMENT` 修正，不能請求使用者核准。
5. 只有 `animation_design_review.md = PASS` 後，協調者才能請求使用者核准該精確受審版本。
6. 只有同一精確版本同時取得獨立審查 `PASS` 與使用者明確核准，才可以進入 `CONTRACT`，忠實轉換成 `pre_build_brief.md`。

獨立審查 `PASS` 不能取代使用者核准；使用者核准也不能取代獨立審查。沉默、未回覆或只編輯檔案，都不算核准。

## 7. 文件修改、重新審查與回退

### 修改 `animation_design.md` 後怎麼處理

使用者可以直接編輯 `animation_design.md`，但每次編輯都會建立新版本。任何新版本都會使先前的審查與核准失效，必須重新完成：

1. 辨識實際變更；
2. 保留使用者原意與措辭；
3. 更新 `DESIGN_READY` 自檢；
4. 執行適當範圍的獨立審查；
5. 審查通過後，再請使用者核准新的精確版本。

不得用舊文字默默覆蓋使用者的編輯，也不得讓任何編輯繞過重新審查。

### 選擇 Full Review 或 Delta Review

| 情況 | 必須採用的審查 | 審查範圍 |
|---|---|---|
| 第一次審查 | Full Review | 整份 `animation_design.md` 與全部 `DESIGN_READY` 條件 |
| 修改演算法語意、主要心智模型、核心視覺隱喻或視覺語意、教學弧線、場景結構或高階節拍 | Full Review | 整份文件與全部 `DESIGN_READY` 條件 |
| 修改影響不確定、可能跨越多個章節，或已暴露先前的不一致 | Full Review | 整份文件與全部 `DESIGN_READY` 條件 |
| 修改明確局部，且完整影響可被追蹤 | Delta Review | 變更文字、所有相依段落、保留的使用者決策、內部一致性及更新後的 `DESIGN_READY` 自檢 |

Delta Review 進行期間，只要發現跨區影響或先前的不一致，就必須立即升級為 Full Review。

### 何時退回 `DESIGN_DEVELOPMENT`

出現以下任一情況時，必須把設計退回 `DESIGN_DEVELOPMENT`：

- 審查發現回歸、矛盾或沒有證據支持的主張；
- 遺失或錯誤改寫使用者決策；
- 任一 `DESIGN_READY` 條件失敗；
- 下游工作發現已核准設計在技術上無效或有實質缺漏。

回退時應把使用者要求的變更保留在決策紀錄中，清楚說明衝突。只有衝突會實質改變核心設計時，才用一個聚焦的核心問題詢問使用者。

一旦回退，所有下游工作都必須停止。修正後的 `animation_design.md` 必須重新通過適當範圍的獨立審查，並重新取得使用者對該精確版本的明確核准，才能恢復下游工作。

## 8. 禁止事項

出現以下任一情況，都代表流程執行失敗：

- 把澄清問題當成主要產物，而沒有完成動畫的教學與呈現設計；
- 提出大問卷、一次向使用者問多題，或把無關決策混在同一批；
- 核心問題沒有提供建議、理由或重要取捨；
- 不準確記錄使用者答案，或悄悄替換成其他選擇；
- 因低影響偏好而阻塞設計；
- 沒有完成心智模型、視覺呈現、教學弧線或高階節拍；
- 在任一 `DESIGN_READY` 條件未通過或仍有阻塞性核心問題時宣告 `DESIGN_READY`；
- 在所有 `DESIGN_READY` 條件通過後繼續提問、補充或擴充設計；
- 在 `animation_design_review.md` 尚未記錄 `PASS` 前請求使用者核准；
- 把沉默、未回覆或未經審查的文件編輯視為核准；
- 在必須使用 Full Review 的情況下使用 Delta Review；
- 設計已回退到 `DESIGN_DEVELOPMENT`，卻仍繼續任何下游工作；
- 在同一精確版本尚未同時取得 `PASS` 與使用者核准前，就開始轉換為 `pre_build_brief.md`。
